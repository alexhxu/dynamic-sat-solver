Dynamic Load Balancing for Parallel SAT Solving

Alex Xu and Alma Zhong

Download the proposal as a PDF

URL

https://alexhxu.github.io/dynamic-sat-solver/

Summary

We will implement the divide-and-conquer parallel SAT architecture described by Le Frioux et al. [1]. We will use MiniSat as the sequential solving engine and focus on the parallel systems problem of dynamically distributing irregular search subtrees across multicore workers. We will compare static partitioning with dynamic work redistribution and evaluate speedup, idle time, scheduling overhead, and wasted speculative work.

Background

A SAT solver determines whether a Boolean formula has a satisfying variable assignment. Modern solvers use conflict-driven clause learning (CDCL): they choose variable assignments, propagate their consequences, learn clauses from conflicts, and backtrack.

We will use MiniSat [2] rather than implement CDCL ourselves. This allows us to focus on parallel scheduling instead of SAT-specific optimizations.

A formula F can be divided on a variable x using

F = (F ∧ x) ∨ (F ∧ ¬x).

Applying this recursively creates guiding paths, or cubes, representing disjoint search subspaces. MiniSat can solve the original formula under a cube using its assumptions interface. The formula is satisfiable if any cube is satisfiable and unsatisfiable only after every cube has been refuted. 

                     F
                 /       \
              x1           ¬x1
            /    \        /    \
         x2      ¬x2    x3      ¬x3
       [W0]    [W1]   [W2]    [W3]      each leaf is a cube solved by one worker

Different cubes can be solved independently, which is where the parallelism comes from, but their running times are extremely unpredictable. Static partitioning may therefore leave most workers idle while one worker processes a difficult cube. The paper addresses this problem by dynamically dividing an active worker's cube whenever another worker becomes idle.

Approach

Each worker will own a MiniSat instance and solve one guiding path at a time. A master thread will track worker states and outstanding subspaces.

Initially, the search space will be divided until each worker has a cube. When a worker proves its cube unsatisfiable, it will request another job. Following Le Frioux et al., the master will select the eligible worker that has spent the longest time on its current cube. The victim will be interrupted at a safe point, and its cube C will be divided into C ∧ x and C ∧ ¬x. One child will be assigned to the victim and the other to the idle worker.

A configurable minimum runtime will prevent newly created cubes from being immediately divided again. We will select the division variable with two heuristics and compare them: MiniSat's variable activity, and the flip-count heuristic from Le Frioux et al. Workers will also export learned clauses and import clauses learned by other workers. A portfolio configuration, in which several MiniSat instances solve the full formula under different random seeds, is a third parallel system we will implement and measure [4]. 

master loop:
    split root cube until every worker has one cube
    while not done:
        wait for an event from a worker
        if worker reports SAT:
            interrupt all workers; return SAT
        if worker reports UNSAT on its cube:
            if no cubes are outstanding: return UNSAT
            victim = active worker with the longest time on its cube
                     (and running for at least min_runtime)
            interrupt victim at a safe point
            x = division variable in victim (activity or flip count)
            give victim   C ∧ x
            give idle one C ∧ ¬x
            share clauses learned since the last split

We will compare these configurations, all built on the same MiniSat workers:

  1. Static partitioning: Initial cubes are distributed once, with no redistribution after workers finish.
  2. Dynamic division: Idle workers trigger division of long-running active cubes, using either the activity heuristic or the flip-count heuristic.
  3. Dynamic division with clause sharing: The same scheduler, with learned clauses exchanged among workers.
  4. Portfolio: Several MiniSat instances solve the original formula with different seeds and no cube division.

Stock single-threaded MiniSat will be our external performance baseline. All parallel answers will be checked against it for correctness.

The Challenge

The central challenge is scheduling an irregular workload whose task sizes cannot be predicted from the structure of the search tree. Our implementation must address the following parallel systems issues:

  • Load balance: Search subtrees at the same depth may have dramatically different solving times.
  • Task granularity: Frequent division provides more parallelism but increases interruption, synchronization, and restart overhead.
  • Steal latency: A worker must reach a safe point before its subspace can be divided, leaving the requesting worker temporarily idle.
  • Work inflation: Separate workers may repeat propagation and rediscover clauses, increasing total CPU work.
  • Termination: A SAT result permits immediate cancellation, while an UNSAT result requires every outstanding subspace to be refuted.
  • Resource contention: Multiple solver instances may compete for shared cache capacity and memory bandwidth.

These issues connect directly to course topics including dynamic scheduling, granularity, synchronization, speculative execution, locality, and scalability.

Resources

We will use MiniSat 2.2 as our sequential engine and implement the parallel scheduler in C++. Our primary reference is the divide-and-conquer component from Le Frioux et al. [1]. Their implementation uses PaInLeSS [3] and MapleCOMSPS; we will reproduce the scheduling design using the smaller MiniSat codebase.

We will select satisfiable and unsatisfiable instances from SAT Competition benchmark collections. We will use instances requiring tens of seconds to several minutes on one core so that scheduling behavior is measurable.

Development and initial evaluation will use the GHC multicore machines. If time and access permit, we will use PSC for higher-core-count experiments.

Goals and Deliverables

Plan to Achieve

  • Integrate MiniSat as the sequential worker engine.
  • Solve cubes using MiniSat assumptions.
  • Implement safe asynchronous interruption.
  • Implement static guiding-path partitioning.
  • Implement the master/worker dynamic division scheduler.
  • Add a configurable minimum runtime before division.
  • Implement SAT cancellation and correct UNSAT termination.
  • Validate all results against stock MiniSat.
  • Evaluate satisfiable and unsatisfiable benchmarks separately.
  • Implement the flip-count division heuristic and compare it with variable activity.
  • Share learned clauses among workers and measure the effect on work inflation and wall-clock time.
  • Implement a portfolio baseline with different random seeds and compare it with divide-and-conquer.

We will measure wall-clock speedup, parallel efficiency, worker idle time, steal count, interruption latency, number of generated cubes, total CPU time, and speculative work discarded after early termination. The questions we will answer are whether dynamic division improves utilization and running time over static partitioning, whether flip-count division and clause sharing change that result, how divide-and-conquer compares with a portfolio, and which overheads limit scalability.

Hope to Achieve

With the planned system in place, we will run the same comparisons at higher core counts on PSC, looking at multi-socket effects, memory contention, and serialization at the master thread. We would also like a short poster demo that solves a small instance live and shows per-worker idle time and steals.

If the Schedule Slips

A static solver with a restricted scheduler would be too narrow: it would not answer the questions above. If we fall behind, we will shrink the benchmark set and the parameter sweep. The system we deliver will still include dynamic division, the flip-count heuristic, learned-clause sharing, and the portfolio comparison, evaluated on GHC.

Success does not require linear speedup. A successful project will demonstrate correct dynamic scheduling and use measurements to explain when it helps or hurts performance.

Platform Choice

Shared-memory multicore CPUs are appropriate because separate cubes require little communication while solving. C++ integrates naturally with MiniSat and provides direct control over persistent worker threads, atomics, condition variables, and cache-aware data structures.

The GHC machines support development and moderate-core-count experiments. PSC would allow us to examine higher core counts, multi-socket effects, memory contention, and possible serialization at the master thread.
